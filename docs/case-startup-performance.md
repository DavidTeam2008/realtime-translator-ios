# 案例：把 200ms 启动目标证伪 —— 一次诚实的负结果

> **一句话结论**：200ms 冷启动目标被最小对照组地板挡住（同口径空壳 App p50=210ms），上一轮启动优化在真机上无显著收益（280ms→279ms，p=0.605），**启动微优化已暂停**。
> 状态：已结案（2026-09-24 暂停）。原始启动过程文档（原 `docs/14`–`docs/18`）随本批文档治理归档删除，全文可从 git 历史取回。
> 口径：未特别说明的数字均来自真机 Release 测量（iPhone 13 / iOS 26.7）；复测需同设备、同构建类型、同命令、同样本量。

## 结论速览

- **目标判定不可达**：最小对照组（空壳 SwiftUI App）同口径 p50=210ms，目标 200ms 落在对照组地板之下，判定 `blocked_by_control_floor`。
- **上一轮优化无效**：真机 A/B 中位数 280ms → 279ms（+0ms，p=0.605）；同版本在模拟器反而测出 -4.6%（p=0.0088）的**假信号**。
- **剩余空间有限**：可优化部分约 64ms（27%），其中首页内容 29ms、外围脚手架约 35ms；46% 是 SwiftUI 框架引导，属框架固有。
- **决策**：暂停微优化；不重启、不用模拟器证明性能；若重启，先改架构/需求变量并重建同口径对照。
- **本案例的价值**：展示"口径先于优化、对照实验、单样本会骗人"的完整证据链，避免下一棒重复劳动。

## 1. 背景与目标

- 这是一次**自主闭环演练**：设定一个激进验收目标（真机冷启动 ≤200ms），验证"能否靠局部优化达成"。
- **为什么是 200ms**：原始文档没有解释目标来源，只把它作为演练验收目标；当时唯一的公开参照是 **Apple 建议首帧 ≤600ms**，200ms 远严于该建议。除此之外不推测动机（原文未说明）。
- **口径必须区分**（最容易搞错的一件事）：

| 口径 | 终点定义 | 当时代码的典型值 |
|---|---|---|
| `AppLaunchTracker`（自埋点） | 进程创建（`sysctl`）→ 首帧提交（延迟一拍打点，逼近 `CA::Transaction::commit`） | 真机冷启动 **240–280ms** |
| XCTest `testColdLaunch` | 到"首页首张卡片可点" | **0.312–0.331s，均值约 0.32s** |
| Instruments App Launch life-cycle | 含进程创建/系统开销与 Debug tunnel | 约 880ms |
| `devicectl process launch` | 隧道耗时 | 约 0.26s，**不是冷启动** |

> 这四种数字都不是同一个终点；混用会直接得出错误结论（见 §4 的方法论修正）。

## 2. 方法与实验设计

1. **真机 A/B（验证上一轮优化）**：对照 `a24038d`（优化前，HEAD~2）vs 优化后 `1b2206d`（当时 HEAD），Release/iphoneos/arm64，同一台真机；给旧版本补上**完全相同**的埋点与终点定义后再比，用置换检验判断显著性。
2. **可行性对照（回答"目标能否达成"）**：临时 detached worktree 中只把首页内容替换为 `Text("x")` 做 control，**保留** App 生命周期、埋点（`AppLaunchTracker`/`EarlyLaunchMark`）、根视图、`onAppear`、`task`、`sheet` 等外围，以及 Release 构建与同一测量命令；control 与 candidate 同设备、同 profile：iPhone 13 / iOS 26.7 / physical / Release / **warmup 3（不计入样本）/ n=20 / 间隔 5s**，指标 `startup.cold.first_frame`。
3. **分段与归因**：C 构造函数测 pre-main；`STORE open took Nms` 直接测真实开库（区别于后台调度延迟）；`body` 首次求值打点（`beginOnce`）拆视图树；另建**空白 SwiftUI App** 在最细粒度上做对照。
4. **消融实验**（真机，每组 3–4 次取中位数）：`NavigationStack`、SF Symbols + 卡片结构、无障碍修饰、首页内容换 `Text("x")` 四项分别验证。
5. **防假信号**：任何启动结论不看单次样本；看中位数差 + 显著性 + 样本量。

## 3. 结果

### 3.1 上一轮优化的真机 A/B：无显著差异

```text
对照(优化前)  中位数 280ms   n=8  CV 7.0%
优化后(当前)  中位数 279ms   n=5  CV 4.6%
改善 +0ms (-0.2%)  置换检验 p=0.605 → 差异不显著
```

同一对版本在模拟器：389ms → 371ms（-4.6%，p=0.0088）——**模拟器给出了真机上不存在的"改善"**。

### 3.2 真机阶段拆分（优化后，中位数 ≈280ms）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| pre-main（dyld + 镜像初始化） | 11ms（n=6，范围 10–13，CV 13%） | 4% |
| App init → environmentReady | ~6ms | 2% |
| **environmentReady → firstFrame** | **~250ms** | **89%** |

- **SwiftData 真实开库只有 12ms**（n=6，范围 12–27ms）——原判断"同步开库是最重的一项"被推翻；把它移出关键路径最多省 12ms，在 280ms 里不可测量。
- 日志里 `storeReady +179ms` **不是开库耗时**，而是后台 `.utility` 任务被调度的延迟（主线程忙渲染时排队）。
- 真正瓶颈是 SwiftUI/UIKit 框架初始化与首次渲染的 ~250ms，上一轮优化没有触及。

### 3.3 空壳对照与完整归因（冷启动 ≈240ms 的最终状态）

空白 App 对照（同机、同口径）：`App init → 首个 body` 空白 App 115–143ms vs Duiyi 117ms（≈0，**框架固有**）；`视图 body → 首帧提交` 5ms vs 89ms（本 App 特有）。消融实验：`NavigationStack` +0ms、无障碍修饰 +3ms、SF Symbols + 卡片结构 +24ms、首页内容换 `Text("x")` 后 `body→appear` 40→11ms、`appear→commit` 74→66ms。

| 段 | ms | 占比 | 性质 |
|---|---|---|---|
| pre-main | 18 | 7% | 框架固有（空白 App 同样） |
| App init → environmentReady | 6 | 3% | 已极轻（延迟开库生效） |
| **SwiftUI 引导（appBody）** | **~110** | **46%** | **框架固有，不可优化** |
| 视图树 body 求值 | 22 | 9% | — |
| 首页内容渲染 | 29 | 12% | 可优化（结构 + SF Symbols） |
| 外围脚手架（commit 阶段） | ~35 | 15% | 可优化（`@Environment`/`.sheet`/`.toolbar` 等） |

**可优化合计约 64ms（27%）**，且这 64ms 的边际收益低于风险与复杂度。

### 3.4 可行性对照：目标被控制组地板挡住

```text
control（最小 Text("x")）  n=20，p50=210ms，CV=2.7%，usable
candidate（当前首页）      n=20，p50=262.5ms，CV=8.3%，usable
目标：200ms                 判定：blocked_by_control_floor
```

结论：**本轮不进入局部启动优化**；也不把 control 的 210ms 宣称为"理论极限"（那只是当前架构下的控制组地板）。正确动作是升级为架构/需求决策。

### 3.5 模拟器结论不能用于真机（双向失真）

| 指标 | 模拟器 | 真机 | 差异 |
|---|---|---|---|
| pre-main | 257ms | 11ms | 模拟器高估 **23 倍** |
| SwiftData 开库 | 124ms | 12ms | 模拟器高估 **10 倍** |
| 总启动 | 459ms | 280ms | — |

失真方向是相反的：模拟器没有 dyld 共享缓存 → 严重高估 pre-main；又跑在 Mac 的 SSD/充裕内存上 → 严重低估 I/O 与缺页。**启动优化必须真机验证，模拟器只能做功能回归。**

## 4. 结论与决策

- **不可达**：200ms 低于空壳对照组地板（210ms），靠局部优化无法达成。
- **暂停**（2026-09-24）：启动耗时已不是短板（真机约 240ms，Apple 建议首帧 ≤600ms 以内）；继续投入 ROI 不划算。
- **已排除方向（不必再试）**：

| 方向 | 实测结论 |
|---|---|
| 二进制重排 | 已正确落地（1479 符号 100% 匹配、`_main` 打头），当前包体下**不可测量**；保留管线，不期待收益 |
| SwiftData 延迟开库 | 真实开库仅 12ms，收益淹没在噪声里；保留可以，但**不应再以"首帧优化"为由加码** |
| 弱链接 FoundationModels/Speech/Translation | pre-main 真机仅 11ms，上限收益 < 10ms，且风险显著 |
| `NavigationStack` / 无障碍修饰 | +0ms / +3ms |
| pre-main 微优化 | 属框架固有（空白 App 对照证明），不要再碰 |

- **明确不要做**：不重启启动微优化；不用模拟器证明性能；不手写 `Order/App.order`（必须由脚本从 Release 二进制再生，且只在 Release 生效）。
- **若要重启**：先改变一个架构级变量（例如把目标改成可达范围，或评估换掉 SwiftUI 场景机），再重建与 candidate 同口径的 control 测量；否则任何优化都无法验证。
- **当前事实源**：排期与验收见 [`04-roadmap.md`](04-roadmap.md)；口径决策见 [`decisions.md`](decisions.md) D1；铁律见 [`../references/contracts.md`](../references/contracts.md) §7。

## 6. 能学到什么（Harness Engineering 视角）

1. **负结果是交付物**：把"目标不可达"连同证据、排除方向、复测入口写入仓库，比继续微优化更有价值——它阻止下一棒重复劳动。
2. **口径先于优化**：起点/终点/构建/设备/样本量任一项不同，结论就无效；本文出现过"89ms vs 5ms 得出 84ms 全可优化"的错误对比，正是终点定义不一致造成的。
3. **对照实验 + 显著性**：单次样本会骗人（首测曾出现 476ms vs 359ms 的"117ms 改善"，交替 5 次后真机差异是 0ms）；结论必须看样本量、CV 与 p 值。
4. **承认框架边界**：46% 是 SwiftUI 框架引导，属于"产品需要的能力"；把它们当敌人去砍，方向就错了。
5. **证据分层**：原始测频数据（trace/run，不入库）→ 结论 JSON/摘要（入库）→ 文档只写可复核线索；这样证据可追溯而不污染仓库。
