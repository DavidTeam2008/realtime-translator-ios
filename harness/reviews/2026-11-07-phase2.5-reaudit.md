## 5. 新发现（P1/P2）

- **P1-A 证据时效的 dirty 盲区**：`freshness_reasons` 用 `git diff <evidence.commit>..HEAD`（`verify-claim.py:113-142`），不检查当前工作树；evidence 自身 `dirty=false` 也不限制当前 dirty。NT8：证据 commit=HEAD + 未提交修改 → still PASS。最小修复：若 `git status --porcelain` 命中 claim 相关路径 → STALE/UNVERIFIED。
- **P1-B `make end` 接受 STALE**：作者机器等价环境 3 条 STALE 仍 exit 0（`Makefile:92-93,98`）；完成门禁只对 FAIL/UNVERIFIED 生效，发布门禁才 strict。最小修复：plan 声明"完成/done"或存在未验证项时，end 对 STALE 判非 0（或提供显式 override）。
- **P1-C 「过程记录」旁注豁免 PASS 绑定**：NT2 证明 `PASS` 行 + `—（过程记录）` 可直接通过；白名单语义（基线/过程/外部/历史/未验证/负向）被用作通用旁路。最小修复：白名单仅在结果单元格不含 PASS 词时生效，或要求同时写"非完成声明/材料说明"。
- **P1-D CI/pre-push 不跑 claim 判定/时效**：`verify.yml:93` 与 `pre-push:41` 只跑 `verify-static`；CI 目前硬校验"计划证据 ID/绑定"，但不校验 evidence verdict/STALE（换机器 xcresult 不可达也不应误伤，属设计取舍）。建议：CI 增加 plan-only 硬校验说明 + 本地 `end/release-check` 作为唯一 claim 门禁；或在自托管 macOS job 跑 `verify-claim-fresh`。
- **P2-A 文档与实现漂移**：`HARNESS.md:107` 仍写「L3 条件成立…evidence 时效/ID 校验待补（Phase 2.5）」；scorecard L3 行仍写「仍缺 commit==HEAD 绑定、证据 ID 硬校验」——这两项已实现（`plan.py`），应更新为"已接线、剩 P1 旁路"；`verify-static 约 4.3s` 实测 8.1s（单测 42→88）；scorecard「3 条 clean-tree evidence PASS」仅在作者机器成立（clone 内 2 条 UNVERIFIED），建议标注"本机"。
- **P2-B 新机器预期未写清**：clean clone 上 `make verify-claim` 会 UNVERIFIED×2（xcresult 缺失），`release-check` 必然红；应在 CONTRIBUTING/HARNESS 明说"证据链只在本机可复核，外部复现以 `make check` 为准"。
- **P2-C 工作树并发编辑**：复核期间 Phase 4 改动（release notes、新 evidence、文档）未在计划「未提交改动」声明 → `make check` 红；这是门禁正确行为，但提交前必须更新计划（handoff skill 已有要求）。

## 6. L3 结论

- **可记达成（有条件）**：本地 `make end` 已能对计划内完成声明做 PASS/FAIL/UNVERIFIED 三值判定；`release-check` strict 阻断发布；CI 的 `verify-static` 对计划证据 ID/`done submitted` 做硬校验（含 commit 绑定）。「完成声明可被否证」从**需要 agent 主动跑**变成**默认收尾动作的一部分**。
- 但以下 P1 未清零，**不建议对宣称 "完整可审计" 之外的能力（L4）**：dirty 盲区、end 对 STALE 非阻断、旁注旁路、CI/pre-push 不跑 claim 判定；真机/性能证据仍只能人工。
